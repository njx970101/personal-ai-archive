# AI-READWRITE: 重要决策记录

每项决策记录背景、选项、理由和复查条件，避免未来 AI 把旧决定当成永恒规则。

## 9bot 模型调用应隐藏回退实现、保留 quickai 入口

- 日期：2026-11-05
- 状态：架构偏好已明确；回退链运行结果尚未确认可用
- 背景：quickai 故障时 9bot/微信可能出现轮次失败 502
- 选择：默认每次先请求 quickai 大肥鱼，失败后请求官方 DeepSeek；DSH 界面只保留现有 quickai provider，内部回退实现不额外增加 provider 名称或 API key
- 核心决策原则：复用已有凭据和 UI 项；通过真实调用验证，不以配置测试代替端到端结果
- 主要理由：保持原有模型入口和 key 管理方式，同时提高 quickai 故障时的可用性
- 未选择的方案：增加单独显示的“9bot 模型回退网关”provider，或创建 relay 专用 API key
- 复查条件/日期：官方 DeepSeek 回退须以真实请求确认认证和网络均成功；故障时检查 relay 日志
- 相关项目或记录：9bot/DSH 模型回退配置；本档案不保存密钥或本机路径

## DSH 账号登录与官方 API key 必须分别核验

- 日期：2026-11-05
- 状态：已确认的排障原则
- 背景：用户说明已登录 DeepSeek 账号；同一时段 relay 使用的 `DEEPSEEK_API_KEY` 请求官方 API 曾得到 401，近期还出现连接重置/HTTP 550
- 选择：区分 DSH 的账号登录通道与 `api.deepseek.com` 的 API key 通道，分别检查；不得由其中一方的登录状态推断另一方可用或不可用
- 核心决策原则：依据具体调用端点和认证类型判断
- 主要理由：网页/桌面账号会话与 API key 是不同认证机制
- 未选择的方案：仅根据“账号已登录”断言 API key 有效，或仅根据 API key 401 断言账号通道不可用
- 复查条件/日期：重新实现回退到 DSH 账号模型时，先验证模型兼容性和真实请求
- 相关项目或记录：`ai-integration.md`、9bot 模型回退排查
